# North Karnataka Taluk Rainfall Dashboard (1996-2025)

Python/Dash re-build of the original R/Shiny + Leaflet dashboard, covering
**only 1996-2025** as requested (the raw parquet actually holds 1901-2025;
`data_prep.py` filters it down).

## 2. Build the processed data (run once, or whenever the raw parquet is refreshed)

```bash
python data_prep.py
```

This implements the pipeline you sketched:

```
IMD Rainfall Data (Parquet, 1901-2025)
        │
        ▼
Data Preprocessing  (data_prep.py)
        │
   ─────┼─────────────────────┬─────────────────
   │                          │                 │
Spatial Join            Weekly Statistics   Monthly Statistics
(112 Taluks, from       (SMW 1-52, per       (Jan-Dec, per
 the shapefile)          taluk/year)          taluk/year)
        │                          │                 │
   ─────┴─────────────────────┴─────────────────
        │
        ▼
Rainfall Database (data/processed/*.parquet)
        │
        ▼
   Dash Application (app.py)
```

Produces:
- `daily.parquet` — daily rainfall 1996-2025 with SMW/month/year columns + district
- `weekly_smw.parquet` — taluk × year × SMW **total** rainfall
- `monthly.parquet` — taluk × year × month **total** rainfall
- `annual.parquet` — taluk × year **total** rainfall + rainy-day count
- `taluk_lookup.parquet` — taluk → district lookup (112 taluks)
- `taluks_4326.geojson` — taluk polygons reprojected to WGS84 for the Leaflet map

I used the **parquet** file rather than the `.rds`, since it's the same data
in a columnar format `pandas`/`pyarrow` read natively and far faster than
round-tripping through R — no functionality is lost.

## The averaging rule (as you specified)

> "if user selects 1996 to 2000, average of one year taken, and after that
> all averages of selected years added and then divided by 5"

Concretely, for a selected date range:
1. For **each year** in the range, compute the **total** rainfall for the
   period of interest (SMW total, month total, or year total).
2. **Average those per-year totals** across the selected years.

This is *mean of yearly totals*, not a pooled mean of raw daily values — it's
what the Annual Average KPI, the weekly (SMW) line chart, and the monthly bar
chart all use. I validated this against your screenshot: Dharwad → Hubballi,
full 1996-2025 range → **687.1 mm/year**, and the Crop Irrigation Calendar's
first 15 weeks (Avg Rain / Max Rain) match your screenshot exactly.

`data_loader.years_in_range()` currently maps a date range to full calendar
years touched by that range (inclusive). If you'd rather truncate to the
exact day-of-year on partial-year selections, that's a one-function change.

## Crop Irrigation Calendar (rebuilt on real crop water requirement data)

This replaced the old flat "<30mm = irrigation required" rule with your
uploaded crop water requirement data
(`data/raw/NIK_All_Crops_SMW_Water_Requirements.xlsx`, sheet
`SMW_Weekly_CWR_Breakdown`), read and turned into an actual calendar by
`crop_calendar.py`. All **7 crops** in that sheet (Rabi Sorghum, Maize,
Cotton, Groundnut, Pigeon Pea, Green Gram, Pearl Millet) are selectable --
tested each one through the live app. Each crop has exactly one variety/soil
type in the sheet, so the dropdown shows crop names only (e.g. "Groundnut",
not "Groundnut - GPBD-4"); the variety is still used internally to pick the
right rows, it's just not surfaced in the UI.

**How the sowing date lines up with the growth-stage data:** each crop's
sheet gives its week-by-week profile (growth stage, Kc, ET0, Weekly CWR)
anchored to a reference sowing week. When you pick an actual sowing date,
the whole profile shifts: whatever SMW your sowing date falls in becomes
"Crop Week 1", and every following crop-week advances one calendar SMW from
there (wrapping past week 52 back to week 1 for a late sowing date). The CWR
figures themselves don't change with the shift -- a crop in its flowering
stage needs the same water whether sown in SMW 35 or SMW 40 -- only which
calendar week (and which rainfall climatology) that stage lands on changes.

**The irrigation decision, per crop-week:**
```
avg weekly rainfall <  Weekly CWR (ETc, mm)  ->  Irrigation Required (shows the deficit, mm)
avg weekly rainfall >= Weekly CWR (ETc, mm)  ->  No Irrigation Required
```
The avg/min/max weekly rainfall for each calendar SMW always comes from the
**full 1996-2025 (30-year) climatology** for the selected taluk -- fixed,
not whatever date range happens to be selected on the Rainfall page -- since
this is meant to reflect the long-term normal. That's also why the page
footnote reads: *"This crop irrigation calendar is generated using the last
30 years (1996-2025) of IMD rainfall data for the selected taluk."*

The page shows 4 summary KPIs (crop duration in weeks, total CWR, total
expected rainfall, net irrigation requirement = the shortfall across the
whole season) plus the full week-by-week table, downloadable as CSV. The
Weekly CWR and Avg Rain columns are highlighted (blue / green) since
they're the two numbers the irrigation decision hinges on, and there's a
short glossary above the footnote explaining Kc, ETc/CWR, and mm for anyone
unfamiliar with the terms.

**Adding more crops:** `crop_calendar.available_crops()` reads whatever
distinct crops exist in the sheet, so adding another one is just appending
its own week-by-week rows (same columns) to `SMW_Weekly_CWR_Breakdown` --
no code changes needed for it to show up in the Crop dropdown.

## Tap-to-select on the map

The sidebar map now always shows all 112 taluks (not just the current
district's): the selected taluk in orange, the rest of its district in pale
orange, and every other district in muted grey — but every polygon is still
clickable. Tapping any taluk anywhere in the region:
1. Updates the District and Taluk dropdowns to match (works even if the
   tapped taluk is in a completely different district than the current one).
2. Loads that taluk's data immediately — no need to press GO.

This is handled server-side: Leaflet's click event only reports the tapped
lat/lon, not which polygon was hit, so `spatial.taluk_at_latlon()` does a
point-in-polygon lookup against the same taluk geometries used to draw the
map (with a nearest-centroid fallback for a tap that lands just outside a
border, which matters most on a small mobile screen). Useful on mobile,
where reaching for a dropdown is slower than just tapping the map.

## 4. Deploying behind IIS (Phase 13)

Your pipeline is: **Dash app → Waitress WSGI → IIS reverse proxy → users**.

Full step-by-step walkthrough (installing ARR/URL Rewrite, wiring up the
reverse proxy, running Waitress as a permanent Windows Service via NSSM,
opening it up beyond your own network, and HTTPS) is in
**[DEPLOYMENT.md](DEPLOYMENT.md)**. Short version:

1. On the Windows server, install IIS with **Application Request Routing (ARR)**
   and **URL Rewrite** (both free MS downloads), and enable ARR's proxy.
2. Run the app with Waitress instead of the Flask dev server:
   ```bash
   waitress-serve --listen=0.0.0.0:8050 app:server
   ```
   (`server` is the Flask instance exposed at the bottom of `app.py`.)
3. In IIS Manager, create a site (or use Default Web Site) and add a URL
   Rewrite rule that reverse-proxies a sub-path to Waitress, e.g. requests to
   `http://localhost/rainfall/*` → `http://localhost:8050/{R:1}`.
4. **If deploying under a sub-path** (not the site root), set the
   `DASH_URL_PREFIX` environment variable (e.g.
   `DASH_URL_PREFIX=/rainfall/`) on the Waitress process, so the app builds
   its asset/API URLs with that prefix — otherwise the page loads unstyled.
   Not needed if the dashboard lives at the site root.
5. Register Waitress as a Windows Service (e.g. via NSSM — Non-Sucking Service
   Manager) so it restarts automatically on reboot, and point Task Scheduler
   at `data_prep.py` if you want the processed tables refreshed on a schedule
   (Phase 13 "Scheduled Data Update").

## Notes / assumptions I made

- SMW = Standard Meteorological Week, `ceil(day_of_year / 7)`, capped at 52
  (days 365/366 fold into week 52) — matches the SMW 1-52 axis in your chart.
- A "rainy day" (used for the rainy-day count in `annual.parquet`, ready for
  Phase 4) is defined as ≥ 2.5 mm, the standard IMD threshold — flag if you
  use a different cutoff.
- All 112 taluk names in the rainfall parquet matched the shapefile's
  `KGISTalukN` exactly, so no name-cleanup step was needed.
